## 詳細所見

### 1. ハーネス
- `CLAUDE.md`は`AGENTS.md`を読み込むだけの1行、`AGENTS.md`はNext.jsの破壊的変更に関する注意書き1つのみ。
- プロジェクト固有の約束ごと（セリフの正本の場所、高齢者向けUIテキストの基準、44pxルールなど）はコードのコメントに散らばっていたが、AIが毎回読む場所には集約されていなかった。

### 2. 小さく作る
- 直近15コミットの大半が1〜3ファイル・100行以下の変更。コミットメッセージも「何をしたか」が日本語で一目で分かる。
- 唯一の懸念点：`app/page.tsx`が「司令塔」としてじわじわ育っており（当時282行）、機能追加のたびに肥大化する構造だった。

### 3. テスト
- テストが1本もなく、テストランナーも未導入。
- ただし`lib/bantou.ts`・`lib/relay.ts`のような「入力を入れたら答えが決まるだけの素直な関数」に分かれており、テストを書く土台自体はすでに整っていた。

### 4. CI
- `.github/workflows`が存在せず、pushしても自動チェックが走らない状態だった。
- 評価時点で`npm run lint`はエラー0・警告5、型チェックも合格。CIを作れば最初から緑で通る状態だった。

### 5. コードの基本
**良かった点**
- 名前が説明書になっている（例：`saveMemoDraft`、`maybeTriggerRelay`）
- コメントが「なぜ」を語っている（例：「メモを先に保存する（生成に失敗しても入力が消えないように）」）
- キャラクター設定・取り次ぎルールがデータ（配列）として`lib/bantou.ts`・`lib/relay.ts`に分離されており、機能追加時にロジックを増やさず配列に1件足すだけで済む設計
- 失敗しても止まらない作り（音声・画像フォールバック、AI生成失敗時もメモは保存済み）
- ログイン確認→入力検証→エラーの翻訳、という3段構えのAPI設計（`app/api/generate/route.ts`）

**指摘事項（このセッションでは未対応）**
- `ResultCard.tsx`と`NoticeDetailPanel.tsx`に、お知らせの型定義・タブ定義（signage/poster/circular）がほぼ同じ形で2箇所存在
- `NoticeDetailPanel.tsx`・`DueDatePicker.tsx`の保存処理が、Supabase側のエラーを握りつぶして常に成功したように見せてしまう
